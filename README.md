# auma-project-3

Панель управления технической документацией: по номеру заказа подтягивает
документы с сайта AUMA и складывает их в общее хранилище с фильтрами,
папками и владельцами файлов.

## Что умеет

- **Регистрация и вход** по email с паролем.
- **Загрузить характеристики** — по номеру заказа скачивает Technical Data Sheet
  с сайта AUMA. Формат выбирается: `web` (htm) или `pdf`.
- **Разбивка по позициям.** Заказ может состоять из нескольких позиций
  (`Pos. 1.0`, `Pos. 2.0` …). Тогда полный файл получает в колонке Article
  все изделия через подчёркивание (`SAEX-07.2_ACEXC-01.2`), а **каждая
  позиция сохраняется ещё и отдельным документом** со своим артикулом
  и попадает в свою папку. Работает одинаково для `pdf` и `web`.
- **Загрузить схему пдкл.** — по номеру заказа получает схему подключения (PDF)
  и попутно определяет артикул изделия.
- **Таблица документов**: File, Data Uploaded, Article, Order, File Size,
  File Owner, Action. **Фильтр есть у каждой колонки.**
- **Две группы в меню**:
  - **Привод** — папки SA, SAEx, SQ, SQEx;
  - **Блоки управления** — папки AC, ACExC, AM, AMExC.
  Группа сворачивается, а при раскрытии показывает документы всех своих папок.
- **Раскладка по папкам по артикулу**: `SQEX-07.2` попадает в `SQEx`,
  `SAEX-10.2` — в `SAEx`, `AM-01.1` — в `AM`. Дерево описано в
  `app/catalog.php`; там же достаточно дописать новую папку.
- **Звезда** — в избранное, **три точки** — меню «Отправить на почту» и «Удалить файл».
- Корзина, счётчик хранилища.

## Технологии

- PHP 8.5 + MySQL 8.4, nginx — без единой внешней библиотеки и без сборки фронтенда.
- Фронтенд: чистые HTML/CSS/JS, стили сняты с макета.

## Структура

```
app/            PHP: конфиг, БД, авторизация, интеграция с AUMA, API
  auma.php      разбор форм AUMA (характеристики и схемы)
  catalog.php   дерево групп и папок — одно место для всей структуры
  api.php       JSON API
  views/        шаблоны страниц
public/         веб-корень (index.php, assets, uploads)
sql/schema.sql  схема базы
deploy/         установка, настройка и обслуживание
```

## Установка на чистый сервер

```bash
# 1. окружение
bash deploy/install-server.sh

# 2. залить файлы проекта в /var/www/auma

# 3. настроить сайт
bash deploy/setup-site.sh
```

Пароль базы генерируется автоматически и лежит в `/root/.auma-db-pass`;
он же прописывается в `app/config.php`.

## Настройка

`app/config.php` (в репозиторий не попадает, образец — `app/config.sample.php`):

- `db.*` — доступ к MySQL;
- `app.upload_dir` — куда складывать скачанные документы;
- `mail.enabled` — **отправка на почту пока выключена**. Кнопка есть, письмо
  пишется в таблицу `email_log` со статусом `stub`. Когда появятся настройки
  SMTP, достаточно заполнить `mail.*` и включить `enabled`.

## Как устроена интеграция с AUMA

Обе функции AUMA — обычные ASP.NET-формы, разобранные по шагам.

**Характеристики**

1. `GET www4.auma.com/webservices/TechnicalDataSheetPublic/request.aspx?lang=en`
2. `POST TypeDdl=Order, numberTB=<заказ>, LanguageDdl=E, FormatDdl=htm|pdf`
3. в ответе ссылка `.../AumaWebService/Data/TDS<заказ>_en-<метка>.<ext>`
4. скачивание

**Схема подключения**

1. `GET www4.auma.com/Schaltplan/AuftragsForm.aspx?Lang=en`
2. `POST OrderOrSerialNo=<заказ>, Button1=execute` — в ответе таблица изделия
   с артикулом
3. `POST RequestBttn=Request wiring diagram` — редирект
   `Redirector.aspx?goto=temp%2fTPA....pdf`
4. скачивание PDF

> **Важно.** AUMA отдаёт `HTTP 500`, если запрос не похож на браузерный.
> Заголовки `Accept`, `Accept-Language`, `Upgrade-Insecure-Requests` и
> `Sec-Fetch-*` в `app/auma.php` обязательны — без них формы «не работают».

## Разбивка по позициям

Позиция заказа начинается пометкой `Pos. N.0`, под которой стоит её `Article`.
Когда позиций несколько, сохраняется и полный файл, и **каждая позиция
отдельным документом** — включая первую. Артикулы всех позиций склеиваются
через `_` и пишутся в Article полного файла.

**PDF** (`pdf_split_positions`) — нужны `pdftotext` (пакет `poppler-utils`)
и `qpdf`, их ставит `deploy/install-server.sh`:

1. `pdftotext -layout` разбирает PDF по страницам и находит `Pos. N.0`
   с её `Article`;
2. `pdftotext -bbox` даёт координаты пометки `Pos.` на странице;
3. позиция занимает страницы со своей пометки до страницы со следующей:
   у первой страницы отрезается всё выше пометки (данные предыдущей
   позиции), у последней — всё ниже пометки следующей;
4. обрезанные страницы готовит `pdftocairo -pdf -nocenter -x -y -W -H`
   (при `-r 72` одна точка PDF равна одному пикселю), затем страницы
   склеиваются через `qpdf --empty --pages`.

> **Зачем обрезка.** Таблица позиции часто переходит на следующую
> страницу: у заказа 13497303 на странице 3 сначала идёт продолжение
> ACEXC-01.2 и только потом начинается Pos. 3.0. Если резать по границе
> страницы, хвост таблицы теряется; если брать страницу целиком — в файл
> позиции попадают данные соседней. `pdftocairo` убирает содержимое
> за пределами заданной области, поэтому в файле остаётся только своя
> позиция.

> **Про подъём содержимого.** `pdftocairo` не уменьшает лист и прижимает
> оставшееся к нижнему краю (`-nocenter`; без него — к середине). Поэтому
> содержимое поднимается к верхнему краю через ghostscript:
> `gs -sDEVICE=pdfwrite -c "<</PageOffset [0 <сдвиг>]>> setpagedevice"`,
> где сдвиг равен «высота листа минус высота оставленной области».
> Без ghostscript обрезка тоже работает, но содержимое остаётся
> по центру листа.

**Web** (`htm_split_positions`) — инструменты не нужны, разметка разбирается
регулярным выражением:

1. позиции ищутся по `<b>Pos.N.0</b>`;
2. позиция занимает разметку **от своей пометки до следующей**; последняя —
   до конца документа;
3. для каждой позиции собирается самостоятельный файл: заголовок,
   стиль AUMA и строка заказа берутся из исходного документа.

Здесь границы точные: разметку можно разрезать ровно по пометке,
поэтому файлы не перекрываются.

Если позиция одна или (для PDF) инструментов нет, документ сохраняется
целиком, как раньше.

> **Про AppArmor.** В Ubuntu у `qpdf` есть профиль AppArmor, который
> запрещает читать файлы из `/var/www` и временные файлы без расширения
> `.pdf` — в журнале это видно как `apparmor="DENIED" profile="qpdf"`.
> Поэтому разбор PDF идёт во временном каталоге и только с именами `*.pdf`.

## Два вида пометок позиций

AUMA отдаёт отчёты двух видов, и позиции в них помечены по-разному.

| Вид отчёта | Пометка | Пример |
|---|---|---|
| обычный | `Pos. N.0` — с заглавной, с точками | `Pos. 1.0`, `Pos. 2.0` |
| другой | `pos N` — строчными, без точек | `pos 1`, `pos 2` |

**Это важно.** Шаблон `Pos. N.0` не видит строчные пометки, и тогда деление
идёт не по позициям: строка `pos N` стоит **перед** строкой `article`,
поэтому попадает в конец предыдущего файла вместо своего. Если у заказа
деление выглядит странно — сначала проверьте, какими буквами помечены
позиции:

```
pdftotext -layout файл.pdf - | grep -inE 'pos[ .]?[0-9]'
```

Обе пометки ищутся одинаково — по координате строки на странице
(`pdf_page_markers` для `Pos.` и `pdf_article_marks` для `pos`),
и режутся одним и тем же кодом (`pdf_assemble_pages`).

## Когда пометок позиций нет вообще

Тогда деление идёт по изделиям: у каждого свой блок со строкой `article`
(строчными), и блок начинается с новой страницы. Артикул берётся из этой
строки, имя файла — из артикула (`_SAR_10_2`, `_AC_01_2`, `_GS_125_3`).

- `pdf_split_articles` — режет PDF по координате строки `pos N`;
- `htm_split_articles` — режет разметку по обёртке вокруг `pos N`
  (в htm это `<b>pos   2</b>`, а не ячейка таблицы).

Общий файл получает склейку артикулов: `SAR 10.2_AC 01.2_GS. 125.3`.

## Правила обрезки — общие для всех видов

Какое бы деление ни было, действуют одни и те же правила:

1. **Хвостов быть не должно.** У первой страницы куска отрезается всё,
   что выше его пометки, у последней — всё, что ниже пометки следующего.
2. **Начало у верхнего края.** Оставшееся содержимое поднимается к верху
   листа, как на первой странице.
3. **Первая позиция (изделие) сохраняет шапку** — выше её пометки ничего
   нет, поэтому лист остаётся целым.
4. **Перекрёстные ссылки внутри блока — это данные блока.**
   Например, в блоке блока управления строка `Mounted to: SAR 10.2` —
   нормальное содержимое, а не остаток соседнего изделия.

Проверять так: сумма размеров частей должна сходиться с полным файлом,
а первая строка каждой части — быть её собственной пометкой.

> **Граница куска считается один раз.** Это правило мы нарушили в htm
> и получили в файлах `AC 01.2` и `GS. 125.3` последние строки
> предыдущего изделия — `Weight : 16,519` и
> `Housing material AL aluminium`. Начало вычислялось дважды: сначала
> правильно отступало к обёртке `<span>` вокруг `<b>pos N</b>`, а потом
> код ещё раз сдвигал его назад, к ближайшему `<tr>`, — а этим `<tr>`
> и оказывалась последняя строка чужой таблицы.
>
> Начало определяется в одном месте: либо обёртка вокруг `pos N`,
> либо тег строки `article`. Повторно отступать назад нельзя.

> **`<title>` — не содержимое.** В собранном htm первым в тексте идёт
> артикул из `<title>`, который добавляется при сборке файла. При
> проверке кусков его легко принять за остаток предыдущего блока.

## Названия строк в характеристиках

В разных отчётах одни и те же строки названы по-разному. Регистр
не важен — `article` читается наравне с `Article`. А вот сокращения
отличаются, и их надо сопоставлять отдельно:

| В правилах | В отчёте другого вида |
|---|---|
| `Terminal plan TPA` | `Terminal plan` |
| `Enclosure protection` | `Enclosure protect.` |
| `Corrosion protection` | `Corrosion protect.` |
| `Set to CLOSE (Nm)` | `set to CLOSE` |
| `Set to OPEN (Nm)` | `Nm in sense of rota` |
| `Explosion protection` | `Explosion protect.` |
| `Position transmitter` | `Position transm. DI` |

Из-за этих расхождений паспорт для отчётов другого вида собирается
не полностью — часть полей остаётся пустой.
